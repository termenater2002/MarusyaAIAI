# Research: Страница авторизации пользователей

## Unknowns / Clarifications Needed
- Какой маршрут считается целевой после успешного входа (личный кабинет, главная или предыдущая страница)?
- Нужна ли капча после N неудачных попыток или достаточно простого предупреждения?
- В каких случаях backend возвращает конкретные коды ошибок (например, аккаунт заблокирован, требуется подтверждение email)?

## Best Practices & References
- Использовать семантическую разметку: `<main>`, `<form>`, подписи для полей (`<label>` + `aria-describedby`).
- Валидация email на стороне клиента + отображение ошибок в текстовом виде и через `aria-live` для экранных дикторов.
- Блокировка кнопки "Войти" во время отправки, индикация прогресса (spinner, `aria-busy`).
- Ссылки "Забыли пароль?" и "Создать аккаунт" должны быть очевидны и доступны клавиатурой.
- Обработка разнообразных состояний ошибки: неверные данные, заблокированный аккаунт, техническая ошибка.
- Использовать HTTPS, не отображать, какой из данных неверен (email или пароль) для безопасности.

## Decision Summary
- Целевая страница после входа — `/dashboard` (можно переопределить позже настройкой).
- Предупреждение о множественных неудачных попытках без капчи на первом этапе.
- Ошибки сервера отображаем в одном блоке с нейтральной формулировкой.

## Alternatives Considered
- Модальное окно вместо отдельной страницы (отклонено: хуже для доступности и deeplink).
- Раздельный ввод логина и пароля по шагам (отклонено: усложняет UX, не оправдано).
- Социальные логины на первом релизе (отложено на будущие итерации).
